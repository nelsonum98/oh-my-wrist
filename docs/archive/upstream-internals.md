# Upstream internals: how oh-my-wrist moves events and usage to the watch

Research note for `.scratch/wrist-agents/issues/01-upstream-internals.md`. Read directly against the fork's source at `~/dev/oh-my-wrist` (branch `research/upstream-internals`, worktree `.claude/worktrees/research-upstream-internals`, HEAD `4ace3ef`). Garmin Connect IQ facts are cited to `developer.garmin.com` / `forums.garmin.com` where the source code alone doesn't settle the question. No source file was modified to produce this note.

## 1. Event model

`src/ohm/provider_types.py` defines `CanonicalEvent` (Pydantic `BaseModel`) — the single internal event type every downstream component consumes:

- `provider: Literal["claude", "opencode"]` — **hardcoded to two values.** Adding Codex means widening this literal.
- `canonical_event`: one of `tool_start, tool_end, session_start, session_idle, session_stop, session_error, file_edit, todo_update, permission_request, permission_reply, command, status, unknown`.
- Provenance/content fields: `provider_event`, `session_id`, `tool_name`, `label`, `path`, `status_text`, `active`, `ts`, `meta`.
- `TOOL_INTENT` dict normalizes provider tool names (`bash`, `edit`, `read`, `web`, `todo`, `permission`, `agent`) into an intent used by the formatter/history-encoder so no component branches per-provider after normalization.

`src/ohm/protocol.py` is the IPC + BLE wire-format module:

- **IPC**: newline-terminated JSON over a Unix domain socket at `/tmp/oh-my-wrist-<uid>/ohm.sock` (Windows: a named pipe). Two message shapes share the socket — legacy `IpcMessage` (Claude-only, kept for old `hook_relay` builds) and `CanonicalIpcMessage` (provider-agnostic, what all current code sends); the daemon detects the shape by the presence of a `"provider"` key.
- **BLE GATT service**: `OHM_SERVICE_UUID = 0FA155B0-...` (a "connection ID" 0-255 can vary one byte of the UUID so co-located users don't cross-pair).
- **Characteristics** (all under the one service):
  - `HISTORY_CHAR_UUID` (`...B1`) — Read+Notify, binary per-event frame.
  - `SESSION_CHAR_UUID` (`...B2`) — Read only, 1 byte (any-provider-active flag).
  - `ALERT_CHAR_UUID` (`...B3`) — Read+Notify, 1 byte haptic-alert code, auto-reset to 0x00 after 500 ms.
  - `STATS_CLAUDE_CHAR_UUID` (`...B4`) / `STATS_OPENCODE_CHAR_UUID` (`...B5`) — Read+Notify, one characteristic **per provider**, compact JSON, ≤100 bytes (`MAX_STATS_LEN`). **There is no third stats characteristic** — a Codex provider needs its own UUID here.
  - `USAGE_CHAR_UUID` (`...B6`) — Read+Notify, compact JSON `{"s":..,"w":..}`, ≤40 bytes (`MAX_USAGE_LEN`). Comment in `protocol.py` states this is "Claude-only — OpenCode has no equivalent"; there is exactly one usage characteristic, single-provider shaped.
- **History frame** (`history_encoder.py`): `ver:1 | icon:1 | flags:1 | len:1 | text:≤18B UTF-8`, total ≤22 bytes (`MAX_FRAME_LEN`), safely under the default ATT MTU of 23 — no BLE Long Write needed. `_classify()` is the single place that maps a `CanonicalEvent` to `(icon, flags, text)`; the watch never receives an icon *name*, only the numeric ID, and owns the history deque/spinner animation itself. Icon IDs (`icons.py` `IconId`) are an explicitly append-only registry mirrored in `garmin/source/IconCatalog.mc` — never renumber/reuse.

## 2. Providers

- **`src/ohm/adapters/claude_adapter.py`** — maps Claude Code hook events (`PreToolUse→tool_start`, `PostToolUse→tool_end`, `Notification→session_idle`, `Stop→session_stop`, `SessionStart→session_start`) into `CanonicalEvent`. It reads only `hook_event_name`, `tool_name`, `tool_input`, `session_id` from the hook JSON (via `HookEvent` in `protocol.py`) — **it does not read `notification_type`**, even though Claude Code's `Notification` hook carries one (see §4).
- **`src/ohm/hook_relay.py`** — the short-lived process Claude Code actually invokes per hook (must finish <100 ms, always exits 0). It re-derives the alert type independently of the adapter (`_determine_alert_type`) and fires-and-forgets a `CanonicalIpcMessage` at the daemon over the Unix socket.
- **`opencode/plugins/oh_my_wrist_opencode.ts`** — OpenCode's plugin API (`tool.execute.before/after` + a generic `event` bus) is translated client-side, in TypeScript, directly into `CanonicalIpcMessage` JSON and written to the same Unix socket. There is no Python-side raw-payload adapter step for OpenCode.
- **No `codex_adapter.py`, no Codex hook/plugin, no Codex CLI subcommand exists anywhere in the fork.** `src/ohm/main.py`'s CLI groups are `hook` (Claude), `statusline` (Claude), an `opencode` subgroup (`install/uninstall/status`), plus `config`/`set-id`/daemon lifecycle commands — no `codex` verb.
- **Watch-side provider-specific code**: yes, in three places, and none of it is a clean provider list a Codex addition can just extend by iterating:
  1. `garmin/source/StatsModel.mc` — hardcodes exactly two module-level `StatsData` instances, `claude` and `opencode`, each fed by its own hardcoded characteristic UUID.
  2. `garmin/source/BleManager.mc` — hardcodes `STATS_CLAUDE_CHAR_UUID`/`STATS_OPENCODE_CHAR_UUID`/`USAGE_CHAR_UUID` as separate `var`s and routes each GATT notification with an `if/else if` chain on UUID equality (lines ~1284-1290).
  3. `garmin/source/OhMyWristApp.mc` / `OhMyWristDelegate.mc` — the widget is a fixed 4-view swipe stack: `[0] OhMyWristUsageView (Claude-only usage bars) → [1] OhMyWristView (history, initial) → [2] OhMyWristStatsView(claude) → [3] OhMyWristStatsView(opencode)`. `_makeView(index)` in the delegate is an index-keyed switch, not a data-driven list.
  4. `IconCatalog.mc` / `Palette.mc` are **not** provider-specific — they're keyed only by the append-only icon ID and flags byte, so no touch needed there for a new provider as such.

## 3. Usage path

Flow: Claude Code → `src/ohm/statusline_relay.py` (installed as the `statusLine` command) → IPC `usage` message → `ble_daemon.py` → `USAGE_CHAR_UUID` → `garmin/source/UsageModel.mc` (parses `{"s":..,"w":..}` via manual substring scan, no JSON library) → `garmin/source/OhMyWristUsageView.mc` (two 10-cell bars, "S" 5-hour and "W" 7-day, screen is annotated "Claude-only").

**Where the 5h/7d numbers originate**: Claude Code pipes a JSON blob to the configured statusLine command on every statusline refresh; that blob's `rate_limits.five_hour.used_percentage` and `rate_limits.seven_day.used_percentage` are Claude Code's own reporting of the account's rate-limit windows (statusline_relay.py's docstring cites `docs.anthropic.com/en/docs/claude-code/statusline`). This is *not* the same code path as Nelson's existing `~/.claude/statusline-command.sh`, which independently calls the Claude OAuth usage endpoint directly (per `.scratch/wrist-agents/map.md`); oh-my-wrist instead piggybacks on whatever Claude Code itself puts in the statusLine JSON's `rate_limits` block. `rate_limits` is documented as present "only for Claude.ai Pro/Max subscribers and only after the first API response in a session" — each window independently defaults to `-1` (unknown) when absent.

**Usage only updates while a session is running — confirmed.** `statusline_relay.py` only runs when Claude Code invokes the configured `statusLine` command, which Claude Code does only while a session/TUI is active (it's a per-render statusline callback, not a background poller). There is no separate poller in the fork that hits any usage API on its own; the daemon's `self._usage` dict just holds whatever the last-received `statusline` IPC message said, indefinitely, until the next session pushes a fresher value. So: (a) usage is stale from the last session the moment Claude Code closes, and (b) usage is entirely absent until the first statusline render of the *first* session ever run with oh-my-wrist installed. The daemon-side push mechanics themselves (`_push_usage`, the periodic 5s/10s keepalive re-push) are already session-independent — they'll re-notify the watch with the last-known cached value even with no session active — but the *value* itself is only ever refreshed by a running Claude Code session.

**Wire payload**: `{"s":<int -1..100>,"w":<int -1..100>}`, compact JSON, UTF-8, enforced ≤40 bytes (`MAX_USAGE_LEN`) — realistic payloads are ~17 bytes, comfortably inside one ATT-MTU-23 notification. `_clamp_pct()` on the daemon side coerces garbage to `-1`. The daemon intercepts `canonical_event == "usage"` **before** it reaches the session-state engine or history frame (`ble_daemon.py::_process_ipc_message`) — a usage update never produces a history-view entry and is silently dropped for any provider other than `"claude"` (`if provider == "claude": ... else: return` with no branch for other providers at all — this is the second concrete Codex-usage gap, alongside the single-provider `USAGE_CHAR_UUID`).

## 4. Haptics

Alert byte written to `ALERT_CHAR_UUID`, held ~500 ms, then reset to `0x00`. Constants (`protocol.py`): `ALERT_NONE=0x00`, `ALERT_IDLE_WAITING=0x01`, `ALERT_SESSION_DONE=0x02`, `ALERT_DESTRUCTIVE=0x03`, `ALERT_AGENT_DONE=0x04`. Two independent places compute the alert type and must be kept in sync (a real footgun for future edits):

- **Claude**: `hook_relay.py::_determine_alert_type()` — `Notification → IDLE_WAITING`; `Stop → SESSION_DONE`; `PreToolUse` + `is_destructive_command()` (`status_formatter.py`, a regex over shell/rm/dd/chmod-777/kill-9/etc.) `→ DESTRUCTIVE`; `PostToolUse` + `get_tool_intent(tool)=="agent" → AGENT_DONE`. Final gating happens in `ble_daemon.py::_send_alert()`, which zeroes the alert if `cfg.haptic_allowed()` is false (respects `haptic_enabled` and the quiet-hours window in `config.py`).
- **OpenCode**: mirrored logic lives client-side in the TypeScript plugin (`alertForToolStart`/`alertForToolEnd`, same `DESTRUCTIVE_RE`, same `AGENT_TOOLS` set) since the plugin talks straight to the daemon without a Python adapter pass.

**"Session done" detection** = Claude's `Stop` hook / OpenCode's `session.completed` event — i.e., the *whole* Claude Code/OpenCode session/turn ending, not a discrete background job. **"Agent completion" detection** = a `PostToolUse` event whose tool name normalizes to the `"agent"` intent (`task`, `subagent`, `dispatch`, `agent` in `TOOL_INTENT`) — i.e., a synchronous **subagent (Task-tool) call returning within the current turn**, not an asynchronous background job.

**Gap for job-level alerts, confirmed against Claude Code's own hook contract** (see `code.claude.com/docs/en/hooks`): the fork registers hooks for only `PreToolUse`, `PostToolUse`, `Notification`, `Stop` (`install.py::_HOOK_EVENTS`). It never registers `SubagentStop`, which Claude Code fires specifically when a subagent finishes and which carries `agent_id`/`agent_type` fields identifying *which* subagent completed — closer to "job name" than anything the fork currently captures. More importantly, the `Notification` hook's payload carries a `notification_type` field (values include `agent_needs_input` and `agent_completed`, per the docs page) that `claude_adapter.py`/`hook_relay.py` **never reads at all** — every `Notification` is collapsed to the same generic `session_idle`/`ALERT_IDLE_WAITING`, discarding the exact "done" vs "needs input" vs (implicitly) "failed" distinction the map.md destination wants surfaced on the watch. *(Confidence: MODERATE — the hook-events list and field names came back from an automated fetch-and-summarize of the live docs page rather than a raw read of the page; the fetched inventory looked broader than expected — `TaskCreated`/`TaskCompleted`, `SubagentStart`, etc. — so an implementer should re-pull `https://code.claude.com/docs/en/hooks` directly and re-verify field names before wiring anything to them.)*

## 5. Install

`src/ohm/install.py` + `src/ohm/platform/macos.py`. The installer performs three steps:

**A. `~/.claude/settings.json` hook patch** (`patch_claude_settings()`): merges into `hooks`:
```
PreToolUse:   [{"matcher": "", "hooks": [{"type":"command","command":"<abs>/oh-my-wrist hook","async":true}]}]
PostToolUse:  [{"matcher": "", "hooks": [<same>]}]
Notification: [{"hooks": [<same>]}]              # no "matcher" key at all
Stop:         [{"hooks": [<same>]}]              # no "matcher" key at all
```
It **appends** to whatever list already exists per event key (`hooks.setdefault(event, [])`, then prunes any *prior oh-my-wrist* entry and appends the current one) — it does not touch or remove entries belonging to other tools. `_ohm_command()` resolves an absolute path (console-script next to `sys.executable`, or `<python> -m ohm <subcommand>`) specifically because Claude Code's hook subprocess PATH won't include a venv `bin/`.

**B. statusLine patch** (`patch_claude_statusline()`): **overwrites the whole `settings["statusLine"]` object** with `{"type":"command","command":"<abs>/oh-my-wrist statusline"}` — a plain 2-key dict — after saving the previous `command` string (only the string, not the whole object) to `~/.oh-my-wrist/prev_statusline` for uninstall/chaining. `statusline_relay.py::_chain_previous()` re-executes that saved command and passes its stdout through untouched, so the user's *displayed text* survives, but any other keys on the original `statusLine` object (padding, refresh interval, etc.) are **not preserved or restored**.

**C. Service registration**: `install_service()` dispatches to `ohm.platform.macos` (this fork's install target) → launchd LaunchAgent, label **`com.oh-my-wrist.daemon`**, plist at `~/Library/LaunchAgents/com.oh-my-wrist.daemon.plist`, `RunAtLoad=true`, `KeepAlive=false`, runs `oh-my-wrist start --foreground`, logs to `~/.oh-my-wrist/daemon.{stdout,stderr}.log`. `PATH` in the plist's `EnvironmentVariables` is hardcoded to `/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin` — no Homebrew `/opt/homebrew/bin`, no `uv`-managed venv bin dir, so any `oh-my-wrist` console script that isn't in one of those four dirs (or resolvable as `shutil.which("oh-my-wrist")` *at install time*, since `executable` is baked into the plist as a literal path rather than resolved at launch) won't be found by launchd. Not a collision, but worth flagging for the build ticket.

### Collision check against `/Users/nelson/.claude/settings.json`

Read directly (no secrets in it). Current file has:
- `hooks.PostToolUse`: one entry, `matcher: "Write|Edit|MultiEdit"` → `scan-secrets-in-writes.sh`
- `hooks.PreToolUse`: two entries — `matcher: "Bash"` → `block-dangerous-bash.sh`; `matcher: "Write|Edit|MultiEdit"` → `protect-env-files.sh`
- `hooks.SessionStart`: one entry, `matcher: "*"` → `herdr-agent-state.sh session`
- No `hooks.Notification`, no `hooks.Stop` keys present yet.
- `statusLine`: `{"type":"command","command":"bash ~/.claude/statusline-command.sh","padding":0,"refreshInterval":10}` — this is the script map.md flags as already fetching the Claude OAuth usage endpoint.

Result of running the installer unmodified against this file at the time:

1. **`PreToolUse`/`PostToolUse`: no collision, additive.** oh-my-wrist appends its own `matcher:""` (all-tools) entries alongside the existing matcher-scoped security/herdr hooks. Claude Code runs every hook whose matcher matches a given tool call, so all four PreToolUse-family hooks and both PostToolUse-family hooks fire independently on every relevant call; oh-my-wrist's is `async:true` so it shouldn't add latency to the security hooks. **Net new**: every tool call now also spawns `oh-my-wrist hook`.
2. **`Notification`/`Stop`: no collision, net-new keys.** Nothing currently occupies them.
3. **`SessionStart`: untouched.** oh-my-wrist does not register a SessionStart hook at all, so herdr's `session` hook is unaffected — but this also means oh-my-wrist has no session-boundary signal independent of the first `PreToolUse`/`Notification`/`Stop` it happens to see, which matters if a "session-independent usage fetch" implementation wants a clean session-start marker.
4. **`statusLine`: real collision, currently silent/lossy.** `patch_claude_statusline()` will overwrite the whole 4-key statusLine object (dropping `padding` and `refreshInterval`) with its own 2-key object, saving only the bare command string `bash ~/.claude/statusline-command.sh` for chaining. The *displayed text* from Nelson's existing statusline-command.sh will still appear (chained via subprocess passthrough), but `padding: 0` and `refreshInterval: 10` silently revert to Claude Code defaults, and uninstall restores only `{"type":"command","command":...}` because the installer never captured the other fields. **A build fix should extend `patch_claude_statusline()`/`remove_claude_statusline()` to round-trip the whole prior statusLine object (as JSON), not just its `command` string.** This is also functionally identical to the "session-independent usage fetch" gap: the existing script and oh-my-wrist's own usage source (`rate_limits` from Claude Code's own statusline JSON) are two *different* signals for the same number, and installing oh-my-wrist as-is doesn't merge or dedupe them — it just chains display text while separately intercepting `rate_limits` for the BLE push.
5. **No collision with `~/.codex/config.toml notify`** (out of scope for this file — that's a Codex, not Claude Code, config surface; see map.md notes that it's already occupied by the Computer Use client). Not re-verified here since it's outside `~/.claude/settings.json`.
6. **launchd label `com.oh-my-wrist.daemon`** doesn't collide with Nelson's `com.nelson.<name>` convention numerically, but it also doesn't follow it; map.md already flags renaming/folding this as an open decision.

## 6. Build and test

- **`tools/build_garmin.sh`**: locates `monkeyc` via `$MONKEYC`, `$CONNECTIQ_SDK_HOME/bin/monkeyc`, or globs `~/.Garmin/ConnectIQ/Sdks/*/bin/monkeyc`; locates a developer key via `$GARMIN_DEV_KEY` or several default paths. Modes: `release` (per-device `.prg` files, one per `<iq:product>` scraped out of `manifest.xml` with `sed`), `store` (single `.iq` package via `monkeyc -e`), `all` (both, default). Output in `build/garmin/`, logs per-device in `build/garmin/logs/`, up to `GARMIN_BUILD_MAX_FAILURE_LOGS` (default 5) failure logs echoed to console.
- **`garmin/monkey.jungle`**: `project.manifest = manifest.xml`; single shared `base.sourcePath = source`, `base.resourcePath = resources`; every one of the ~140 products in the manifest gets an identical `<product>.resourcePath = $(base.resourcePath)` line (no per-product resource overrides currently exist).
- **`garmin/manifest.xml`**: `epix2pro51mm` **is present** in the `<iq:products>` list (confirmed by direct read — line present verbatim, alongside `epix2pro42mm`/`epix2pro47mm`). App id `85566b11c3c9e615f33df10d37a69377`, `minApiLevel="3.1.0"`, permissions `BluetoothLowEnergy` + `Communications`, single language `eng`.
- **`tests/`**: 28 pytest files under `tests/`, all Python-side (daemon, adapters, protocol, session state, install, status formatter, statusline relay, history encoder/frame, notification spacing, usage daemon path, hook_relay, CLI). **No Monkey C / Connect IQ simulator test files exist in the repo** — watch-side code has no automated test coverage in this fork; `tests/test_garmin_connection_id_menu.py` tests the *Python* connection-ID logic, not the watch UI.
- **Can the Connect IQ simulator exercise BLE?** Not on its own, and not against a real Garmin watch. Per Garmin's own developer documentation: BLE peripheral/central communication in the simulator requires a physical **Nordic nRF52 DK** board flashed with Garmin-provided firmware, acting as the simulator's actual BLE radio — "the Connect IQ Simulator will use the nRF52 DK board BLE chipset to communicate with nearby BLE devices per the Connect IQ Bluetooth Low Energy APIs." Without that board, the simulator cannot open a real GATT connection to the desktop daemon or a physical watch. This matches the fork's own code: `ble_daemon.py`'s Linux BlueZ bonding comments explicitly discuss "when the nRF52 DK reboots or the Garmin simulator resets" — i.e., the fork's own upstream dev/CI setup already assumes an nRF52 DK-backed simulator for BLE testing, not a bare simulator. **Practical implication for this build**: testing against the real epix Pro 2 51mm over BLE (sideloaded `.prg`) is the only way to validate the BLE path end-to-end; the plain simulator can validate UI/layout/Monkey-C logic only.

## 7. Upstream branches `bugfix/mac-os-ble-disc` and `feature/release-pypi`

Both are **already fully merged into this fork's `main`** — confirmed with `git merge-base --is-ancestor <branch> HEAD` against the current worktree (true for both). Nothing to cherry-pick or port. The relevant macOS-stability commit is `ad92e34 "Fixed BLE daemon startup crash on macOS"`, present on both branches and on `main`. Its fix (already in the code read for §1-6 above): CoreBluetooth-backed `bless` on macOS crashes if a notify-capable characteristic is registered with a non-`None` cached value; the fix registers `HISTORY_CHAR_UUID`/`ALERT_CHAR_UUID`/`STATS_*_CHAR_UUID`/`USAGE_CHAR_UUID` with `None` and seeds their real values only *after* `server.start()`. It also adds `_corebluetooth_subscribe_via_monitor`, because CoreBluetooth never calls `write_request_func` for CCCD subscribe writes the way BlueZ/Windows do — macOS subscribe detection instead piggybacks on the connection-state poll in `_connection_monitor_task()`. Anything building on this fork already has both fixes; no further macOS BLE-stability work is inherited from these branches.

### Gap: weekly-only usage for two providers (Claude + Codex)
- `src/ohm/protocol.py` — `USAGE_CHAR_UUID`'s payload is currently Claude-only, 5h+week. Per map.md ("Weekly only... Out of scope: 5-hour rate-limit windows"), the redesigned payload drops `s` entirely and needs a second provider's weekly number — either widen the JSON schema to `{"claude_w":.., "codex_w":..}`-style two-key payload on the existing characteristic, or add a second `USAGE_CODEX_CHAR_UUID`. Given `MAX_USAGE_LEN=40` bytes there's ample room to keep one characteristic.
- `src/ohm/ble_daemon.py::_process_ipc_message` — the `canonical_event == "usage"` branch is hardcoded `if provider == "claude": ... else: return` (§3) — this silently drops any Codex usage message today; needs a per-provider branch or a merged `self._usage` shape.
- `src/ohm/statusline_relay.py` — currently the only usage *source*; needs either a second entry point that Codex-side tooling can call (Codex has no statusLine-equivalent hook to piggyback on the way Claude Code's does), or replacement by the session-independent poller below (which would supersede this file for both providers).
- **Watch**: `garmin/source/UsageModel.mc` (currently parses exactly `s`/`w` keys; comment says "Claude-only" — needs redesign for 2 providers × 1 weekly bar each, or 2 rows relabeled), `OhMyWristUsageView.mc` (currently draws exactly 2 rows "S"/"W" for one provider — needs 2 rows for 2 providers instead, dropping the 5h row per the out-of-scope decision).

### Gap: session-independent usage fetch
- This is the biggest architectural change of the four. Today, `statusline_relay.py` is the *only* path that ever refreshes `self._usage` on the daemon (§3) — it only fires while Claude Code is actively rendering a statusline, i.e., only during a live session.
- **What to touch**: a new, independent poller — most naturally a `launchd`-scheduled (or daemon-internal `asyncio` periodic task in `ble_daemon.py`, alongside the existing `_periodic_stats_task`) process that calls the usage-quota source(s) directly on a timer, not gated on any session being open. Nelson already has exactly this pattern working (`~/.claude/statusline-command.sh` hitting the Claude OAuth usage endpoint directly, per map.md) — reusing/adapting that call, plus an equivalent for Codex/ChatGPT's subscription usage endpoint, is the natural template. Both source endpoints are noted as **unofficial and may change** (map.md) — build in a fallback-to-stale/-1 path matching the existing `_clamp_pct`/`-1` sentinel convention.
- `src/ohm/protocol.py`/`ble_daemon.py` — the daemon already has a session-independent *push* mechanism (`_push_usage` re-notifies the last-known cached value every 5-10s regardless of session state) — only the *source* of the value needs to become session-independent; the push plumbing does not need to change.
- `src/ohm/install.py`/`platform/macos.py` — either fold this poller into the existing `com.oh-my-wrist.daemon` launchd job (simplest: the daemon calls out on its own timer) or register a second scheduled job; the existing plist's hardcoded minimal `PATH` (§5) will need to include wherever `op`/curl/whatever fetches the token/endpoint lives if credentials come from 1Password.
